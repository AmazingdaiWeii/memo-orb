为什么不是「无脑固定右下角」

窗口比面板大 2 × CHROME_INSET，球永远占窗口两个相邻角之一。 默认球位（工作区右边缘、垂直偏下）球恰好落在窗口 se 角 —— 手柄放上去就是压在球上，直接复现 2026-10-07 那次「球彻底失去交互」的卡死。

球占了 se → safeCorner() 自动把角退到对角 nw， 两条边（这里是 上/左）照常随方向翻。

为什么不能直接用 CSS resize: both：它只改元素的 CSS 尺寸、不动 BrowserWindow —— 面板撑大了但窗口没变，多出来的内容直接被裁到窗口外，用户看不到任何变化。真要跟手就得每帧一次 setBounds，而主进程每次都要 clamp + 重算方向，拖拽途中方向翻转会剧烈抖动。所以架构上必须「自定义手柄 + IPC」，但视觉可以照抄原生。

「边」和「角」走的是两套规则（v3 新增，最容易踩）：
·边走 freeEdges() —— 贴球的两条边拖了没用，必须随方向翻。
· 角走 safeCorner() —— 用户指定了偏好角（默认窗体右下角 se），不跟着方向乱跳；只有 se 正好被球占了才退到对角。
用真实常量算过 7 种常见球位，se 在其中 3 种会被球压住（含默认球位）—— 完整验算见 probe/corner-vs-ball-geometry.mjs（23 项断言）。

同轮修的另外两个 bug：
① shell.js 结尾连着写了两遍 main() → 装了两套 UI：两个右键菜单实例（点「重命名」时 A 关了 B 还在屏幕上盖住输入框）、两个原生 Menu.popup() 抢事件（输入框右键没反应）、16 条手柄。已删重复调用 + 加 main._done 幂等守卫。
② 右键菜单 z-index 从 5 提到 9 —— 手柄是 6 且 DOM 在菜单之后创建，会把弹到边缘的菜单盖住、点不动，这就是「右键 ui 又消失」的根因。
