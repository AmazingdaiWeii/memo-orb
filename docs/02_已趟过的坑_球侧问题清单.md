## 3. P1-A —— 用户实机反馈（2026-10-22 凌晨，**当前修复主线**）

> 全部来自用户亲口描述 + 截图。每条都给了根因定位，**改之前先备份该文件**。

### P1-U1　毛玻璃作用对象**反了**（最高优先；与 v1 的 P1-1 不是一回事）

- **用户原话**：「我实际上已经把它改成了只对对话框和输入框以及其它菜单的类似框架生效，而不对对话背景进行遮罩，但是目前这个功能反过来了。」
- **现在的实际形态**：
  - `helper/assets/floating.css:2289-2292` 给 `.bg-layer` 加了 `filter: blur(20px) saturate(1.1); transform: scale(1.12)` ⇒ **背景图自己被糊了**（用户要的正好相反）；
  - `floating.css:137-138` 给 `#panel` 的 `backdrop-filter: blur(30px)` ⇒ **糊不到东西**，因为 `#bg-stack` 是 `#panel` 的子元素、`z-index:-1`，画在 panel 背景**之上**，不在它的 backdrop 里；
  - 视觉结果：背景糊、框架不糊 = 完全反过来。
- **根因一句话**：`#bg-stack` 的**层叠位置错了**（在 panel 内部），不是「透明窗口不能和毛玻璃共存」。
- **正解（三条路，推荐第 1 条）**：
  1. **把 `#bg-stack` 移出 `#panel`**，作为 `body` 下的兄弟层：`position:absolute; inset:var(--chrome); z-index:0; border-radius:var(--panel-radius); overflow:hidden;`，`#panel` 提到 `z-index:1`。这样背景清晰可见、`#panel` 的 `backdrop-filter` 真正糊到背景 ⇒ 对话框/输入框/菜单是毛玻璃，背景不糊。同时删掉 `.bg-layer` 的 `filter`/`transform`。
  2. 保留结构，在 `#bg-stack` 之上、内容之下单独加一层玻璃（多一层 DOM，效果等价但更绕）。
  3. 只用「半透明底色、不加模糊」——**不推荐**，用户明确要毛玻璃框架。
- **验收（必须人眼）**：真机打开面板 → 背景图**清楚**（能认出画面内容）；对话框/输入框/菜单后面的背景**被糊**；窗口四角**仍是圆角**（没被合成成直角）。
- **禁止**：删 `backdrop-filter`。

### P1-U2　环菜单的「通透度圆环」无效

- **用户原话**：「环形菜单上本身有一个调整毛玻璃通透度的进度条，目前它是无效状态，它原本的作用是能够调整对话框内的毛玻璃效果。」
- **现状链路（已核实是通的，别怀疑接线）**：
  `helper/assets/ring-menu.js:126-136`（外圈拖动 `opacityFromPoint` → `bridge.opacity`）→ `src/main.mjs:3079` `orb:ring-opacity` → `saveStoredPanelOpacity` 落盘 `logs/window-state.json` → 回推 `orb:panel-opacity` → `helper/assets/shell.js:3436-3442` 设 `--panel-opacity` → `floating.css:40/79` 的 `--panel-bg: rgba(…, var(--panel-opacity))`。
- **为什么"无效"**：它改的是**面板底色的 alpha**，不是模糊强度；而面板底色之上压着**不透明的背景图**（`#bg-stack`），底下又是被 `.bg-layer` 糊过的图 ⇒ alpha 从 0.3 拖到 0.9，视觉上几乎看不出差别。
- **与 P1-U1 同一根因**：修完 P1-U1 后，`--panel-opacity` 才会真正表现为「玻璃浓淡」。
- **再加一层**：用户语义是「调毛玻璃效果」，建议这个环**同时**驱动新增的 `--panel-blur`（绑 `#panel` 的 `backdrop-filter` 半径，例如 12px→40px），透明度只是副作用。改完在环菜单里给实时预览（`ring-menu.js:132-134` 已有 `--panel-preview`，顺手对齐）。

### P1-U3　抽屉左上「喜欢的」被对话视图的按钮压住；右上 `+` 与 `×` 并排

- **用户原话**：「左上角，我喜欢的和历史对话的 ui 重合了。」
- **根因**：`#history`（左上时钟，进对话历史）与 `#new-conversation`（右上 `+`）是 `#panel` 的绝对定位子元素（`floating.css:211-217`：`top:18px`，左 `12px` / 右 `12px`，`z-index:3`），**抽屉打开时没有被隐藏**。而 `body.bili-history-open #panel` 只调 `padding-top`（`:2346-2349`），absolute 元素不吃 padding ⇒ 两个按钮照旧钉在面板顶部，正好压在「喜欢的」标题和右上角那颗 `×` 上。
- **修**：在 `floating.css:972` 那组互斥规则里补 `#history` 与 `#new-conversation`（五个抽屉统一口径，别只补一个）：
  ```css
  body.history-open #history, body.history-open #new-conversation,
  body.impression-open #history, body.impression-open #new-conversation,
  body.api-config-open #history, body.api-config-open #new-conversation,
  body.theme-open #history, body.theme-open #new-conversation,
  body.bili-history-open #history, body.bili-history-open #new-conversation { display: none; }
  ```
- **验收**：抽屉打开 → 左上只有「喜欢的」标题，右上只有一颗 `×`；关掉抽屉 → 两个按钮回来。

### P1-U4　「我喜欢的」数据源错了（**设计变更，不是补一个参数**）

- **用户原话**：「我原本设计的是，我喜欢的**是它自己浏览 B 站看到的视频**，而非是我点赞后才会被加入到我喜欢当中。」
- **现状（已核实）**：
  - `src/bili-history.mjs:213` 有 `markLiked(bvid, cid, {reason, comment})`，但**唯一调用点是 `src/main.mjs:4588`**，挂在 `action === 'like'` 分支上 ⇒ **只有用户点「赞」按钮才会写 `liked`**；
  - `bili_watch` 没有「标记喜欢」的参数（orb 亲口报的，见 §5-O1），她自己看片时**一个字都写不进去**；
  - 结果：`data/bili-history.json` 6 条记录 `liked` 全 `null` ⇒ 「我喜欢的」栏永远空。
- **要做的不是加参数，是拆语义**：
  1. `liked` 拆来源：`likedBy: 'orb' | 'user'`（或两个独立字段）。**「我喜欢的」只显示她自己的**；用户点的赞留在行内「已赞」状态里，不进这一栏；
  2. 给 `bili_watch` 加 `liked`（布尔）+ `reason`（她那句话）⇒ 看完自己决定并写入；
  3. 「想看却没看成的」也要能记（用户要的是她浏览的足迹，不只是已发生的动作）。
- **风险**：评论是**公开发言、不可撤回**（见 P1-B2），喜欢是**可撤回**的，别把两者合并成一次写。
- **验收**：她自己看一条 → 抽屉「我喜欢的」出现该条并带她写的理由；用户点「赞」→ 该条**不**出现在「我喜欢的」里（或按她最终拍板的口径显示）。

### P1-U5　抽屉没有滚动条；底部工具条是直角

- **用户原话**：「压根没有下拉的滑动进度条」「这个 ui 是直角边……应该换成圆角」。「滑动进度条存在于两个地方：喜欢的视频下方、看过的抽屉中的下拉」。
- **根因 A（无滚动条）**：`#bili-history` 只有 `position/gap/padding-top`（`floating.css:2356-2364`），**既没有 `flex:1 1 auto` / `min-height:0`，也没有 `overflow-y:auto`**。它是 `#panel`（column flex）的子项，内容一长就溢出，浏览器不给滚动条。对照：`#transcript` 与 `#history-list` 都写了 `overflow-y:auto`（`:905`、`:1325`）。
- **根因 B（直角）**：`.bili-history-foot`（`:2715-2730`）用 `position:sticky; bottom:0; background:var(--panel-bg)` 铺了一条**无圆角**的横带，压在 14px 圆角的卡片旁边 ⇒ 视觉突兀；`.bili-more`（`:2547`）自身也没有容器边框/圆角。
- **修的顺序（用户明确要求）**：**先 P1-U4 把「我喜欢的」喂上数据 → 再动滚动**。数据是空的，滚动条改了也看不出效果。
- **修法**：
  ```css
  #bili-history { flex: 1 1 auto; min-height: 0; overflow-y: auto; overscroll-behavior: contain; scrollbar-width: thin; }
  ```
  滚动条样式要与「看过的」抽屉统一（用户说两处都要有滑块）；`.bili-history-foot` 加 `border-radius: 12px`，底色改带圆角的胶囊（或移出滚动容器，别用底色遮罩）。注意 `[hidden]` 复位那条别丢（`:2332-2336`）。
- **验收**：条目多到超出 → 出现可见滑块，能滚到底且「刷新/清空记录」不被挡；两处滚动条外观一致；底部不再直角色带。

### P1-U6　注入块「正在对话时不显示，重开对话才显示」

- **用户原话**：「正在对话时这部分提示词不会显示出来，但是当重新打开对话时，这部分提示词就会出现。」（截图里露出的是 `（现在是 2026-10-22 00:18（周四））`、`（账户余额 ¥8.25…）`、`<memory_update path="MEMORY.md">` 整段记忆全文）
- **根因（一行对上）**：`src/brain.mjs:1069-1076` 有两套文本——
  - 广播给 UI：`yield { type: 'user', text: String(userText ?? '') }` ⇒ **干净原文**；
  - 落盘：`this.sessionStore.appendMessage(sessionId, { role:'user', text: persistText })`，而 `persistText`（`:1046`）= `baseTailParts.join()`，包含 **时间行 + 余额行 + `drift.text`（即 `<memory_update>` 块）**；
  - `helper/assets/shell.js:2566` 渲染用户气泡时直接 `bubble.textContent = block.text`，**没有任何剥离**；
  - ⇒ 实时显示 `userText`（干净）；重开历史读 `messages.jsonl`（脏）⇒ 露出注入块。
- **附带危害（比显示问题更贵）**：`data/conversations/*/messages.jsonl` 里每条用户消息都带着当时的**时间、余额、整篇记忆更新块**，下一轮会被当"历史对话"重新读回并再次发给模型 ⇒ 上下文膨胀 + 重复回灌旧记忆。
- **修法（三步，缺一不可）**：
  1. `persistText` 只落**用户真实说过的话**（`userText` + 确属用户输入的 `extraTail`）。时间、余额、`drift` 一律只进 `tailText`；
  2. 兼容旧数据：历史渲染再加一层兜底剥离（去掉尾部 `（现在是 …）`、`（账户余额 …）`、`<memory_update …>…</memory_update>`），否则已污染的 jsonl 会一直露；

### 13.1 「B 站页面莫名其妙出现在对话框里」= `[hidden]` 被自己的 `display:flex` 压死

**根因**：为了让「看过的视频」抽屉能滚，我给它加了 `#bili-history { display: flex; … }`，
**忘了给「它自己」补 `[hidden] { display: none }`**（只给子元素补过）。
`[hidden]` 只是 UA 样式表里一条低权重的 `display:none`，被我们自己的 `display:flex` 一压就失效
⇒ `hidden` 属性形同不存在 ⇒ 抽屉**永远开着**，和对话内容叠在一起。

**修**：`floating.css` 补 `#bili-history[hidden] { display: none; }`。

**为什么之前没被抓住**：探针只逐条点名断言，没有「随手加个 `display` 就出事」的通用防线。

**新增 S14d（通用不变量）**：文档里**任何**挂着 `hidden` 属性的元素，computed `display` 必须是 `none`。
- 只查「祖先里没有 `display:none`」的那些（祖先不渲染时后代本来就不显示，不算漏光）；
- **豁免 `#panel`**：它收起靠的是 `opacity:0 + scale(0.18)` 那 300ms 动画，身上的 `hidden` 只是状态标记，真 `display:none` 会让展开动画跳变；
- **反向对照做过**：把 `#bili-history[hidden]` 故意写成 `display:flex` 重跑，S14d 立刻红（报 `["bili-history", …]`）。

### 13.2 顺手抓到一个同类的潜伏 bug：`#attach-strip`

S14d 一上线就报出 `attach-strip`：它也是 `display:flex` 且没有 `[hidden]` 复位
⇒ 没附件时那条 **8px 高的空条子照样挂在输入框边上**（`position:absolute; z-index:3`，会抢走一小条点击）。

### 14.2 实测：老接口是**100% 错**，不是「50% 偶发」

用真实账号对本项目账本里的视频连打 8 次 `GET /x/player/v2?aid=&cid=`：

| | 结果 |
|---|---|
| 拿到「URL 里的 aid/cid == 被请求视频」 | **0 / 8** |
| 拿到别人的字幕 | 5 / 8，且能反查出那条**真实存在**（请求「深海猎捕之王」，回来的是「最贵订单！叫代驾去新疆」的字幕，aid/cid 自洽） |
| 压根返回 0 条轨道 | 3 / 8 |
| 加 `buvid3` 后再并发 8 次 | 仍然 0 / 8 |
| **换成 `GET /x/player/wbi/v2`（WBI 签名）** | **own=true，一次就中** |

所以你当年要「小批量并发 × 5 批 + 抖动」才偶尔拿到——那是因为**没有签名**：

- 老接口只作为「没有签名能力」时的兜底，仍然照抄你的并发 + 抖动，但**拿到的必须过归属核对**。

## §17 语音播报 · 适配层（2026-10-22 下午，**只有取音频这一半**）

用户口径：先做一个示例开源出去，别人想接别家自己改适配口径即可。本轮只做**「文字 → 音频字节」**。

### 新增文件

| 文件 | 职责 |
|---|---|
| `src/tts/parse.mjs` | 火山回包解析（NDJSON / 单 JSON / `header.code` 三种形状）+ 错误码翻人话 |
| `src/tts/volcano.mjs` | 火山适配器 + **变体矩阵**（8 个组合，逐个试） |
| `src/tts/openai.mjs` | OpenAI 兼容 `/v1/audio/speech`（覆盖绝大多数别家） |
| `src/tts/index.mjs` | 统一入口 `createTts()`、配置读写、provider 注册表 |

### 为什么要有「变体矩阵」

用户手里有一条火山 key，但**不知道它属于哪条产品线**。火山几条线的差异是三处同时变：

1. **资源 ID**：`volc.service_type.10029`（大模型合成）/ `seed-icl-2.0`（复刻 2.0）/ `volc.megatts.default`（复刻 1.0）
2. **鉴权头名字** —— 同一个厂商改过名：现行文档 `X-Api-App-Key`，早期 v3 文档 `X-Api-App-Id`；
   另有单 key 通道 `X-Api-Key`
3. **请求体形状**：`req_params` 型（unidirectional）vs `text_prompt` 型（create / seed-audio）

所以 `probe()` 会把有意义的组合列出来逐个试，**探到就停**（每次尝试都是真实计费），
成功的变体 id 记住、可回填配置，之后 `speak()` 直接用。

### 已经写进代码的坑

- **复刻 2.0 必带 `additions.model_type=4`**，漏了会**静默回落 1.0**，情绪指令随之失效且不报错。
- 回包是 **NDJSON 多行**，整段 `JSON.parse` 会抛 ⇒ 被误判成「没音频」。
- 错误码可能在顶层、也可能在 `header.code`。
- `45000010` 的真实含义是 **API Key 本身无效**，不是头写错、不是网络问题（她之前踩过）。
- 复刻类变体**缺 speaker 时提前失败、不发请求**（不白花一次钱）。
- OpenAI 兼容通道回的是**二进制**，`res.text()` 会得到一串乱码；`baseUrl` 四种写法都要接住。

### 这一层**没做**什么（下一轮）

- ❌ 播放。主进程没有音频输出能力，必须丢给渲染层 `new Audio(blobUrl)`。

- ❌ autoplay 策略（项目从未设过 `autoplay-policy`，后台自动播报可能被拦）。
- ❌ 分句 / 排队 / 打断。

- ❌ **没有接线**：`src/tts/` 现在没有任何地方 import。别把「文件在」当成「功能通了」。

## 19. 语音播报落地（2026-10-22）：真的开口说话了

### 三段分工（别再混在一起想）

| 层 | 文件 | 干什么 | 不干什么 |
|---|---|---|---|
| 适配 | `src/tts/volcano.mjs` / `openai.mjs` | 文字 → 音频字节 | 不播、不落盘 |

| 播放 | `helper/assets/shell.js` | `new Audio(blobUrl)`，播完 `revokeObjectURL` | 不合成 |

主进程 `src/main.mjs` 只做接线：`case 'assistant'` → `speech.feed(ev.text)`，
`finalize()` → `speech.finish()`，`setTurn(true)` → `speech.stop('新回合')`。

### mp3 即用即抛（用户 2026-10-22 的问题：会不会越来越多）

**不会。** 整条链路只在内存里走一趟：
主进程 `Buffer` → IPC 的 base64 字符串 → 渲染层 `Blob` + `createObjectURL` →
`audio.ended` 那一刻 `revokeObjectURL`。
`speech-playback-e2e` 的 **V7** 钉住这条（`created === revokes`）。

### 四道「挂了也不报错」的墙（这才是本轮的主要工作量）

| 墙 | 不修会怎样 | 修法 |
|---|---|---|
| CSP 缺 `media-src` | `new Audio(blobUrl)` 被静默拦掉，console 只提 media-src，一字不提语音 | `floating.html:12` 加 `media-src 'self' blob: data:` |
| autoplay 策略 | 后台到点播报 `play()` 被 reject（`NotAllowedError`），日志里啥也没有 | `src/main.mjs` 顶部 `appendSwitch('autoplay-policy','no-user-gesture-required')` |
| `revokeObjectURL` 时机 | 不 revoke = 内存只涨不还；revoke 太早 = 播到一半断 | `ended`/`error` 回调里 revoke，先摘 `src` 再 revoke |
| 队列遇错不推 | 第一句失败后 `drain()` 永远等那个序号 ⇒ 整场哑掉 | 失败写 `null` 当**墓碑**占位，指针照走 |

## 20. 出厂包把「打包者自己的微信凭据」搬进了新机器（2026-10-22，已修）

现象：拿到出厂包的人在设置页看到微信显示「已连接」，而那个 bot 是打包者自己的。

根因不在打包，在运行期迁移。`src/wechat.mjs` 的 `createWechatCreds().load()` 在
`<dataRoot>/wechat.json` 不存在时会调 `migrateCreds()`，从**宿主自己的**
`~/.dsh/omni-bridge-config.json` 的 `channels.weixin` 里把 `botToken`/`botId`/`userId`
整包搬过来；数据根是 `join(ROOT,'data')`，于是搬到了新机器的包目录里。
任何装过 DSH + omni-bridge 的机器首启都会中招。

放大它的第二件事：UI 徽标当年只看 `botToken !== ''`（`helper/assets/api-config.js`），
不看 `enabled`，所以哪怕桥从没启动、一条消息都没收发过，也照样报「已连接」。

修法三条：

- 新增配置键 `adoptHostWechatCreds`（默认 `false`）。`createWechatCreds` / `createWechatBridge`
  都收这个开关；`tools/export-factory.mjs` 生成出厂 config 时强制写 `false`。
  开发机 `config.json` 显式 `true`，保住原来的便利。
- 徽标分三档：`已连接`（`enabled` 且 token 在）/ `已配对 · 未启用` / `未连接`。
  提示行也跟着分三支，不再把「token 还在但开关关着」说成能用。
- 删掉已被写进包目录的 `data/wechat.json`，并把 zip 重打一遍。

同类形状（**还没修**，下次碰）：

- `src/providers.mjs` 会从 `~/.legacy/lc-local-backend/providers/auth.json` 复制 API 密钥；
- `src/memory.mjs` 的 `dataRoot()` 在无 `ORB_DATA` 时同样回落 `~/.legacy`。

规矩：以后任何「从宿主机器搬资源」的动作，必须是**显式开关 + 默认关**，且开关本身要写进出厂 config。

教训一句：打包干净度只在「生成那一刻」被检查过，覆盖不到「第一次运行之后」。
出厂包的正确验法是**在一台没有 `~/.dsh` 的干净机器上首启**，不是在自己机器上看一眼。
